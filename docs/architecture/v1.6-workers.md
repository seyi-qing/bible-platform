# v1.6 — Workers, Redis, Notifications and Background Jobs

## What changed

The API is now a producer of asynchronous work rather than the place where every expensive operation executes. A dedicated `services/worker` process consumes BullMQ queues backed by Redis.

Queues:
- `ai`: Bible study generation and persistence.
- `notifications`: database notification creation plus Expo Push delivery.
- `search-index`: idempotent Bible chapter/verse indexing.
- `audio`: audio processing boundary; real transcoding/CDN work can be attached later.

Jobs use explicit IDs for idempotency, exponential retry with jitter, bounded concurrency, completion/failure retention, and graceful shutdown. BullMQ workers move failed jobs into the failed state and support automatic retry/backoff. citeturn0search2turn0search5

## AI flow

`POST /api/v1/ai/study` now creates an `ai_jobs` record and enqueues an `ai` job. The client polls `GET /api/v1/ai/jobs/:id`. The worker retrieves indexed Scripture, calls the configured model, validates returned citations against retrieved passages, persists the assistant message, and marks the job completed.

## Notifications

Authenticated clients register push tokens through `POST /api/v1/notifications/devices`. Notification jobs persist an in-app notification first, then deliver eligible Expo push tokens. Provider delivery is deliberately isolated to the worker so HTTP requests do not wait on push-provider latency.

## Readiness

`GET /api/v1/health/ready` now verifies PostgreSQL and Redis rather than only checking that the Node process is alive. This matches the purpose of readiness checks: the service should only receive traffic when its required dependencies are available. citeturn0search3

The worker also exposes a lightweight `/health` endpoint on port 4010 for container orchestration. It checks PostgreSQL before reporting healthy.

## Important limitation

This release still needs a real dependency install/build/test run in CI because this development environment does not have registry access. The repository remains statically audited and must pass `pnpm install --frozen-lockfile`, typecheck, tests, migrations, container build and deployment smoke tests before production.
