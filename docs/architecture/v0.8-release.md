# v0.8 — Community, Moderation & Notifications

This release adds the first social layer without making the Bible application dependent on a public social feed.

## Core boundaries

- A user can own or join groups.
- Public groups can be joined directly; private groups require an invitation/approval workflow in the next moderation pass.
- Every post/comment is checked against active group membership before access.
- Reports are persisted as moderation work items.
- Notifications are stored in the user's account and can later be delivered through push/email channels.

## Roles

`OWNER` → `ADMIN` → `MODERATOR` → `MEMBER`.

The current API establishes the role field and ownership model. Full role-management endpoints belong in the moderation hardening pass.

## Notification architecture

The database notification is the source event. A worker will eventually fan out the event to:

1. in-app notification
2. push notification
3. optional email

Expo's notification system supports local notifications and remote push notifications, while production push delivery requires a development/production native build rather than relying on Expo Go for Android remote notifications. The provider is therefore kept behind a notification service boundary. 

## Moderation

Reports deliberately don't delete content immediately. They create a review record with a status. Future admin tooling will allow moderators to:

- review report evidence
- warn users
- remove content
- suspend memberships
- suspend accounts
- resolve/dismiss reports
- maintain an audit trail

## Security note

NestJS guards are used for authenticated routes and resource membership checks. Authentication and authorization remain separate concerns; group membership is an authorization decision, not merely proof that the caller is logged in.
