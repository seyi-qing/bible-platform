# v2.0 Release Engineering

## Purpose

v2.0 turns dependency installation and system verification into a fail-closed release process. It does not claim that a build or test passed unless CI actually executed it.

## Release contract

A release candidate is not releasable until a network-enabled CI runner has:

1. Installed dependencies from a committed `pnpm-lock.yaml` using `pnpm install --frozen-lockfile`.
2. Applied every migration to an empty PostgreSQL database.
3. Passed workspace typechecks.
4. Built web, admin, API, worker, packages, and mobile targets that are supported by CI.
5. Passed API unit/security tests.
6. Started PostgreSQL, Redis, API, and worker services successfully.
7. Passed authorization/failure-boundary integration tests.
8. Installed the required Playwright browser and passed E2E tests.
9. Uploaded test reports and logs on failure.

## Why this is fail-closed

The repository intentionally does not contain a hand-written lockfile. A fabricated lockfile would create false reproducibility. CI therefore fails immediately until a real lockfile is generated by pnpm in a network-enabled environment and committed.

## Security scope

The verification suite prioritizes OWASP API Security Top 10 concerns, especially object-level authorization, authentication, property-level authorization, resource consumption, and function-level authorization.

## Browser testing

Playwright is configured for stable CI execution. CI should use one worker unless the suite is explicitly sharded. Browser dependencies are installed by Playwright in the CI job rather than assumed to exist on the runner.

## Final human release checks

Before production deployment, a human owner must verify:

- Bible translation/content licenses
- audio licenses
- production secrets
- AI provider terms and spend limits
- backup/restore procedure
- domain/TLS configuration
- push-notification credentials
- privacy policy and terms
- monitoring and incident contacts
